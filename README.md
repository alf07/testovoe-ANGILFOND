# README

## 🐳 Запуск проекта через Docker

В корне проекта находится **Dockerfile**, который собирает образ с **PHP 8.4**, клонирует репозиторий, устанавливает зависимости **Composer** и запускает встроенный сервер **Laravel** на порту **8000**.

---

### 1. Сборка Docker-образа

```bash
docker build -t notification-app .
```

При необходимости можно переопределить аргументы сборки:

```bash
docker build \
  --build-arg BRANCH=main \
  --build-arg APP_ENV=local \
  --build-arg APP_DEBUG=true \
  -t notification-app .
```

---

### 2. Запуск контейнера

#### Базовый запуск (SQLite)

```bash
docker run -p 8000:8000 notification-app
```

После запуска приложение будет доступно по адресу:

```text
http://localhost:8000
```

---

### 3. Настройка окружения

#### Вариант 1. Передача переменных окружения

```bash
docker run -p 8000:8000 \
  -e APP_ENV=production \
  -e APP_DEBUG=false \
  -e DB_CONNECTION=sqlite \
  -e DB_DATABASE=/var/www/html/database/database.sqlite \
  notification-app
```

---

#### Вариант 2. Использование постоянного SQLite-файла

Создайте файл базы данных:

```bash
touch database/database.sqlite
```

Запустите контейнер с монтированием файла:

```bash
docker run -p 8000:8000 \
  -v $(pwd)/database/database.sqlite:/var/www/html/database/database.sqlite \
  -e DB_CONNECTION=sqlite \
  -e DB_DATABASE=/var/www/html/database/database.sqlite \
  notification-app
```

---

#### Вариант 3. Подключение к внешнему MySQL

Сначала запустите MySQL:

```bash
docker run -d \
  --name mysql \
  -e MYSQL_ROOT_PASSWORD=root \
  -e MYSQL_DATABASE=laravel \
  -p 3306:3306 \
  mysql:8
```

Затем запустите приложение:

```bash
docker run -p 8000:8000 \
  -e DB_CONNECTION=mysql \
  -e DB_HOST=host.docker.internal \
  -e DB_PORT=3306 \
  -e DB_DATABASE=laravel \
  -e DB_USERNAME=root \
  -e DB_PASSWORD=root \
  notification-app
```

> **Для Linux** вместо `host.docker.internal` используйте IP-адрес хоста или добавьте параметр:
>
> ```bash
> --add-host=host.docker.internal:host-gateway
> ```

---

### 4. Выполнение миграций и заполнение тестовыми данными

Получите идентификатор контейнера:

```bash
docker ps
```

Выполните миграции и сиды:

```bash
docker exec -it <container_id> php artisan migrate --seed
```

---

### 5. Запуск обработчика очереди

По умолчанию контейнер запускает только веб-сервер.

#### Отдельный контейнер

```bash
docker run -d notification-app php artisan queue:work
```

#### Или внутри уже работающего контейнера

```bash
docker exec -d <container_id> php artisan queue:work
```

---

### 📌 Полезные команды

Просмотр запущенных контейнеров:

```bash
docker ps
```

Остановка контейнера:

```bash
docker stop <container_id>
```

Просмотр логов:

```bash
docker logs -f <container_id>
```

Вход внутрь контейнера:

```bash
docker exec -it <container_id> bash
```

## 🚀 Как запустить проект без Docker

Проект разработан на **Laravel 13** с использованием **SQLite**, **очередей Laravel** и **Pest** для тестирования.

### Требования

- PHP 8.3+
- Composer
- SQLite

### 1. Клонировать репозиторий

```bash
git clone <repo-url>
cd <project-folder>
```

### 2. Установить зависимости

```bash
composer install
```

### 3. Создать файл окружения

```bash
cp .env.example .env
php artisan key:generate
```

### 4. Настроить базу данных

По умолчанию проект использует SQLite.

Для локальной разработки рекомендуется создать файл базы данных:

```bash
touch database/database.sqlite
```

и указать путь к нему в `.env`:

```env
DB_CONNECTION=sqlite
DB_DATABASE=/absolute/path/to/database/database.sqlite
```

### 5. Выполнить миграции и сидирование

```bash
php artisan migrate --seed
```

### 6. Запустить приложение

```bash
php artisan serve
```

После запуска приложение будет доступно по адресу:

```
http://localhost:8000
```

### 7. Запустить обработчик очереди

В отдельном терминале выполните:

```bash
php artisan queue:work
```

Для локальной разработки можно использовать синхронный драйвер:

```env
QUEUE_CONNECTION=sync
```

Однако для проверки работы очередей рекомендуется использовать `database`.

### 8. Запустить тесты

```bash
php artisan test
```

или

```bash
composer test
```

> **Примечание**
>
> В проекте присутствует Composer-скрипт `setup`, автоматически создающий `.env`, генерирующий ключ приложения и выполняющий миграции.
Для большей гибкости рекомендуется выполнять перечисленные выше шаги вручную.

# 🏗 Архитектурные решения

При разработке были использованы следующие архитектурные решения.

| **NotificationChannelInterface** | Единый контракт для всех каналов отправки уведомлений.
Позволяет легко добавлять новые каналы без изменения существующей логики. |

| **NotificationChannelFactory** | Динамически создаёт экземпляр обработчика на основании конфигурации из таблицы `notification_channels`.
Позволяет управлять каналами через базу данных. |

| **DTO (`NotificationData`)** | Используется для передачи данных между слоями приложения.
Обеспечивает строгую типизацию, улучшает читаемость кода и исключает использование неструктурированных массивов. |

| **Очереди (`SendNotificationJob`)** | Отправка уведомлений выполняется асинхронно,
благодаря чему пользователь получает ответ сразу, а длительные операции выполняются в фоне. |

| **NotificationService** | Содержит основную бизнес-логику приложения (поиск пользователя, создание истории, постановка задач в очередь).
Контроллеры остаются максимально простыми. |

| **History** | Хранит историю отправки уведомлений, количество попыток, ошибки и текущий статус.
Позволяет получать информацию о состоянии отправки и проводить аудит. |

| **NotificationStatus (Enum)** | Исключает использование "магических строк", обеспечивает типобезопасность и упрощает поддержку статусов уведомлений. |

| **FormRequest** | Валидация полностью вынесена из контроллеров в отдельные классы (`SendNotificationRequest`, `HistoryRequest` и др.),
что делает код чище и облегчает повторное использование правил. |

| **UserChannel** | Позволяет пользователю иметь несколько каналов доставки (Email, Telegram и др.) с независимыми адресами назначения. |

| **notification_channels** | Конфигурация каналов хранится в базе данных (код канала, обработчик, активность),
благодаря чему новые каналы можно подключать без изменения бизнес-логики. |

| **Unit и Feature тесты** | Покрывают основные компоненты системы (Factory, Service, Job, Controllers).
Использование `RefreshDatabase` обеспечивает изоляцию тестов. |

# 🚀 Что можно улучшить для production

Несмотря на то, что текущая реализация полностью решает поставленную задачу, для промышленной эксплуатации я бы добавил следующие улучшения.

## Реальная интеграция с внешними сервисами

Сейчас каналы (`EmailChannel`, `TelegramChannel`) выполняют демонстрационную отправку.

Для production необходимо:

- подключить Laravel Mail;
- реализовать интеграцию с Telegram Bot API;
- добавить обработку HTTP-ошибок;
- настроить таймауты;
- корректно обрабатывать исключения внешних сервисов.

---

## Повторные попытки и отказоустойчивость

Добавить:

- Dead Letter Queue;
- более гибкий `backoff` в зависимости от типа ошибки;
- механизм повторной обработки неуспешных уведомлений.

---

## Мониторинг и логирование

Использовать специализированные инструменты:

- Laravel Horizon.

Также добавить:

- Correlation ID;
- структурированное логирование;
- сбор метрик (время обработки, количество успешных и ошибочных отправок, размер очередей).

---

## Кэширование конфигурации каналов

Конфигурация таблицы `notification_channels` изменяется редко.

Вместо обращения к базе при каждой отправке можно использовать:

```php
Cache::rememberForever(...)
```

с автоматическим сбросом кэша после изменения конфигурации.

---

## Выделение сервиса истории

Логику работы с историей уведомлений целесообразно вынести в отдельный `HistoryService`.

Это позволит лучше соблюдать принцип **Single Responsibility Principle (SRP)**.

---

## Улучшение работы с каналами пользователя

Добавить:

- приоритеты каналов;
- фильтрацию неактивных каналов;
- проверку корректности destination;
- резервный канал при ошибке отправки.

---

## Безопасность

Для production необходимо реализовать:

- аутентификацию через JWT;
- политики доступа;
- ограничение частоты запросов (Rate Limiting);
- защиту API.

---

## Оптимизация базы данных

Добавить индексы для наиболее используемых полей:

- `user_id`
- `status`
- `channel`
- `sent_at`

Это позволит значительно ускорить поиск и построение отчётов.

---

## Production-инфраструктура

Для промышленной эксплуатации рекомендуется использовать:

- Supervisor для постоянной работы очередей;
- Laravel Horizon для мониторинга очередей;
- Redis в качестве драйвера очередей;
- выполнение оптимизаций:

```bash
php artisan optimize
```

---

## Расширение функциональности

В дальнейшем можно добавить:

- шаблоны уведомлений (Blade);
- приоритеты отправки;
- возможность отмены необработанных уведомлений;
- поддержку дополнительных каналов (SMS, Push, WebSocket и др.).

---

## Интеграционные и нагрузочные тесты

Помимо существующих Unit и Feature тестов, можно добавить:

- интеграционные тесты взаимодействия с внешними API;
- нагрузочные тесты очередей;
- тестирование производительности системы под высокой нагрузкой.
